# 记忆体系

记忆被刻意分成两层，边界清晰，职责不重叠。

**会话记忆**由 LangGraph 的 checkpointer 承担，按 thread_id 保存某一轮对话的
完整消息历史，属于"本次及近期会话"的短期上下文。它解决的是多轮指代问题：
用户先说"这个项目的技术栈是什么"，再问"那它的部署方式呢"，第二个问题里的
"它"能被正确解析，靠的就是会话记忆。

**全局记忆**由业务层自己维护，存放在独立的 SQLite 数据库的 profile 表中，
保存跨会话长期稳定的用户信息，例如用户希望被如何称呼、偏好的语言、所属团队、
长期关注的项目事实。它与会话记忆分开存储，因为二者的生命周期完全不同：
会话记忆随会话结束而失去价值，全局记忆则要永久保留。

全局记忆在**构建智能体时**被拼接进系统提示词，因此模型每次回答都自然"带着"
这些信息，无需用户在每轮重复说明。记忆发生变更（新增或删除）时，版本号自增，
智能体的缓存键随之失效并自动重建，从而在"记忆及时生效"与"不重复构建智能体"
之间取得平衡。

**为什么用结构化表而不是向量检索**：本项目的记忆是"精确事实"（用户明确说了
什么），而不是"模糊语义回忆"。按主键去重的 profile 表天然满足"同一主题只保留
最新值、不重复注入"，注入成本是常数级，也不需要额外的嵌入模型与相似度调参。
向量检索式的长期记忆更适合海量非结构化回忆场景，本项目暂不需要。

记忆的注入量有上限：单条记忆的长度、注入条目的数量都被限制，避免模型写入
超长文本把系统提示词撑爆。写入时会校验键与值的非空与长度，长度超限直接报错
而不是静默截断，防止用户以为记住了、实际存的是残缺内容。
