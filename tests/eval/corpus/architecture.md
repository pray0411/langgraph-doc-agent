# 系统架构

Pray 的核心是一个基于 LangGraph 构建的 **ReAct 通用智能体**。整个系统围绕一张
状态图展开，图中只有两个主要节点：模型节点（model）与工具节点（tools）。

模型节点负责推理与决策：它读取当前的消息历史，决定是直接给出回答，还是请求
调用一个或多个工具。工具节点负责执行：把模型请求的工具调用真正跑起来，把结果
作为观察（observation）写回消息历史，然后控制权交回模型节点，形成循环。

循环的终止条件是模型不再请求工具、而是直接输出文本答案。为了防止模型陷入
无休止的工具调用，状态图设置了递归上限（recursion_limit），一旦触达就中断执行
并给出可读提示，而不是把异常栈抛给调用方。

会话状态由 **checkpointer** 管理。本项目使用 SQLite 作为后端，按 thread_id
持久化每个会话的完整消息历史，因此服务重启后对话上下文不会丢失。这一点也是
多轮对话能够工作的基础：调用方不需要自己携带历史消息，只需要复用同一个
thread_id。

需要注意的是，checkpointer 返回的消息列表是**整个会话的累积历史**，而不是
本轮新增的消息。因此任何"本轮的统计"（例如本轮调用了哪些工具、本轮命中了哪些
文档来源）都必须先按最后一条用户消息切分，否则会把历史轮次的数据算进本轮。

架构上刻意做了一个取舍：状态图只负责编排与记忆，具体能力（检索、联网、文件
读写、命令执行）全部下沉为独立工具。这样新增能力只需要注册一个工具函数，
不必改动状态图本身。
