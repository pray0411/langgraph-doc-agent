# 工程质量：CI、测试分层、覆盖率缺口与已知问题

本文记录 README「测试与质量」一节背后的完整信息：CI 首次运行暴露的问题、测试套件的密封机制、覆盖率缺口明细，以及质量门禁的设计理由。

## 1. CI 首次运行：八个 job 里七个失败

CI 在 **Windows + Linux × Python 3.10/3.12/3.13** 六个组合上运行，**不提供任何 API Key，也不提供 `.env`**，用于证明"测试通过"在别人的机器上同样成立。Badge 点进去可看到运行结果、覆盖率报告与失败详情（artifact 中包含 `junit/*.xml`、`coverage.xml`、`report/report.html`）。

它第一次跑就是红的，且失败的三类问题在本机**全是绿的**：

1. **pytest 矩阵全红且失败面一致**：`mcp_server.py` 顶层 `from fastmcp import FastMCP`，而 CI 未安装**可选**依赖 `requirements-mcp.txt`。本机 venv 顺手装过 mcp 相关包，于是"环境缺可选依赖"这一事实被本机掩盖。顺此线索还发现 **`requirements-mcp.txt` 本身根本装不上**——`mcp==1.22.0` 与 `fastmcp==4.0.3` 依赖链冲突，`pip install -r` 直接 `ResolutionImpossible`，即"照文档安装 MCP 依赖"从未成功过，是本机环境手工装出来的假象。
2. **ruff 报错**：本机从未跑过 lint。GitHub 注释只截前 10 条，本机跑一遍才看到实际是 75 条。
3. **E2E 红在 XSS 用例**：前端自写的 Markdown 渲染器未过滤 `javascript:` 伪协议链接。该问题后端全覆盖也发现不了，只有真浏览器能发现——这正是 E2E 存在的理由。

三条都属于"本机绿、CI 红"的典型症状。一上 CI 就全绿，往往说明门禁太松，而不是代码干净。

## 2. 测试分层

| 层 | 位置 | 覆盖内容 |
|---|---|---|
| 元测试 | `tests/test_metatest.py` | 测试套件自检：同名用例、环境密封性、自证式用例、版本号单一来源、CI 配置有效性 |
| 安全模型 | `tests/test_security_model.py` | 把安全承诺写成断言：默认拒绝的命令分级表、写→跑必须被拦（`test_write_then_run_is_gated` 直接复刻该攻击链）、DNS rebinding 拒绝、SSRF 目标收敛、会话数上限、413、工具面三方一致 |
| 单元 | `tests/test_core.py` | 纯函数与模块级行为：检索、记忆、反思、成本估算、命令分级 |
| 契约 | `tests/test_server_writes.py` | 真实 HTTP 打写接口：上传 / 删除 / 重命名 / 重建索引 / prepare→confirm 授权链 / 命令执行 |
| 集成 | `tests/test_agent_loop.py` | 本地假 OpenAI 兼容服务驱动真实 ReAct 工具循环（不联网、不花钱、确定性） |
| 多 provider | `tests/test_provider_contract.py` | 6 个 provider 的配置解析与请求构造契约（不真调 API） |
| 质量评估 | `tests/test_retrieval_eval.py` | recall@3 / MRR 带阈值门禁，固定纯 BM25 并报告模式 |
| 前端 E2E | `tests/e2e/` | Playwright：金路径 + XSS 注入 + 畸形 Markdown（主测试 job 中整体 skip，真跑在独立 job） |
| 性能基线 | `tests/test_perf.py` | 检索 P95、SSE 首字、并发检索（`PERF_WRITE_BASELINE=1` 可重新生成基线） |
| CLI | `tests/test_cli.py` | 命令行入口与参数校验 |
| 日志审计 | `tests/test_logging_audit.py` | 结构化日志与凭据脱敏 |

安全承诺之所以写成断言：这些修复如果只写在文档里，下一次改动就会悄悄退回去——本次改造前的"CSRF 校验"正是如此，代码在、测试在，但测试断言的是**漏洞行为**。

## 3. 测试套件的密封机制

测试结果不依赖开发者本机环境，靠三层封堵（均在 `tests/conftest.py`）：

1. **`.env` 层**：会话级把 `dotenv.load_dotenv()` 替换为空操作。原因：`config.py` 在模块级调用 `load_dotenv()`，任何一次模块重导入都会把本机 `.env` 的真实 Key 灌回 `os.environ`，"删环境变量"式的隔离会被击穿——本地全绿、CI 必红，而且本地那次全绿是真去调了付费接口。
2. **代理层**：清空 `urllib.request.getproxies` 与 httpx 的 `get_environment_proxies`。原因：Windows 上 `getproxies()` 会回退读注册表里的系统代理，装了代理软件的机器上，连"指向 127.0.0.1 的本地假模型服务"都会被绕出去拿到 502，失败信息看起来完全像产品缺陷。
3. **网络层**：包装 `socket.connect`，只放行回环地址；需要真实外呼的用例必须显式加 `@pytest.mark.allow_network`（该标记由 `_network_marker_gate` 真正读取，未标记的网络访问会被拦下）。副作用目录（docs / index / generated / data / logs）全部隔离到临时目录。

## 4. 覆盖率：现状与缺口

实测（`pytest tests --cov=. --cov-branch`，287 条用例全绿）：**总覆盖率 81%**（语句 2700 / 未覆盖 471，分支 872 / 部分覆盖 133），门禁 70%。

| 模块 | 覆盖率 | 缺口 |
|---|---|---|
| `server.py` | 71% | 读接口与写接口主体已覆盖；未覆盖：会话导出、`/api/config` 的完整校验分支、`/api/mode` 的 ollama 可用性探测、SSE 与流式异常分支。缺口集中在需要真实浏览器或长期运行守护线程才能触发的路径 |
| `tools.py` | 79% | `fetch_url` 白名单 / 重定向 / 超限分支、`run_command` 的失败与交互分支、`_bocha_search` 真调用 |
| `retriever.py` | 86% | jieba 缺失时的 bigram 降级、语义编码器异常路径、索引损坏重建分支 |
| `graph.py` | 88% | 纯函数覆盖充分；未覆盖部分流式异常分支与 recursion limit 边界 |
| `runterm.py` | 85% | 会话数上限、有界队列溢出与丢行上报已覆盖；未覆盖进程被外部杀掉后的回收分支 |
| `approvals.py` | 92% | nonce 两阶段已覆盖；未覆盖 TTL 过期清理的并发路径 |
| `config.py` | 91% | 环境变量告警与 `CHUNK_*` 兜底分支 |
| `memory.py` / `logging_setup.py` | 93% / 91% | SQLite 异常路径、日志轮转边界 |
| `mcp_server.py` | 75% | stdio / HTTP 双模式的进程级启动未覆盖（需真起 MCP 客户端） |
| `static/index.html` | 由 E2E 覆盖 | 未覆盖：代码块执行、设置面板、上传 UI |
| `desktop.py` | 0%（排除统计） | pywebview 窗口需真实 GUI |

这些数字的边界：它们是在**未安装 `sentence-transformers`** 的环境下测得的（语义相关代码走降级分支）。装了 torch 的机器上 `retriever.py` 的分支覆盖会不同——覆盖率不可跨环境直接比较，这也是检索指标必须带模式标签的原因。

覆盖率回答"代码有没有被执行"，变异测试才回答"测试能不能抓住 bug"。因此项目额外配置 `[tool.mutmut]`，对 `approvals.py` 与 `retriever.py` 做变异测试（只挑逻辑分支密集、测试充分的小模块；对 `server.py` / `graph.py` 做变异会让单次运行从几分钟涨到几小时）。覆盖率门禁定在 70 而非 90：70 是当前真实水平，先防止倒退，再逐步抬升。

## 5. 其他工程约定

- **版本号单一来源**：仓库根 `VERSION` 文件，`config.APP_VERSION` 与 `pyproject.toml` 均引用它，避免 desktop.py / pyproject / git tag 三处不一致
- **依赖分层**：`requirements.txt`（运行时）、`requirements-dev.txt`（测试与 lint）、`requirements-mcp.txt`、`requirements-desktop.txt`。pytest 从运行时依赖移入开发依赖，避免部署镜像无谓携带测试工具链
- **显式声明测试套件的直接依赖**：`pyyaml` 是读取检索评估集所必需。它此前只是 langchain-core 的传递依赖——如果上游换掉 pyyaml，评估集会静默 skip，而被 skip 掉的质量门禁看起来和"通过了"一样绿
- **lint 配置入库**：代码中早有 `# noqa` 标注，但 ruff 配置从未提交，导致"本机 lint 通过"不可复现
- **句柄泄漏**：`ResourceWarning` 默认可见但不作为错误——用例里的临时连接只在 GC 时释放，GC 时机不确定，设为 error 会得到随机的 flaky 结果。真实泄漏已由被测代码确定性修复（runterm 关闭管道、memory 关闭连接）。严查时用 `pytest tests/ -W error::ResourceWarning`
